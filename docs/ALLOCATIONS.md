# Immutable settled-cost allocation (partial RCO-003/005)

BudgetStore adds `allocate(context, {budgetId,expectedBudgetRevision,reservationId,lines}, commandId)` and `loadAllocation(context,budgetId,reservationId)`. Records live in the Resources OWN operational database using the unchanged pinned Evidence SQL SDK; no other engine's DB or payment/provider endpoint is accessed.

Only a listed human owner budget manager who is ALSO a current stored budget operator may record/read allocations, for the exact reservation purpose. The owning project lock precedes current operator/source reads and cached acknowledgement lookup. Host authentication/current roles/configuration remain trusted; no external Identity query/action fence is claimed.

Each line is exactly `{projectId,contributorId,units}`. IDs are bounded opaque accounting labels, not evidence of a registered person/project or cross-project authority. At most256 distinct project/contributor pairs and64KiB of lines, safe nonnegative integer units, exact balancing to the stored settled charge, one unchanged unit and no implicit conversion. Zero-cost settled records may have zero allocations. Unsettled/released reservations cannot be allocated. Stored labels remain private; do not place private identities/research in reusable fixtures.

One deterministic `cost-allocation` record per budget/reservation, immutable revision1. Its source contains the actual budget storage key/exact edition, reservation/purpose/effect/unit/total, exact historical settlement receipt and unique hash-chained charge sequence/hash. Both current recorded charge and original budget edition are checked on read/replay. Receipt references are historical bookkeeping: this does NOT independently re-attest an external charge, contributor entitlement, licensing, taxes, invoice or payment.

Expected budget revision applies to the first write; current manager/operator/purpose/source checks also apply before historical cached replay. The original command ID/fields return the original immutable snapshot after unrelated budget revisions. A second ID cannot allocate the same charge twice or change its allocation. Allocation/audit/outbox commit atomically in SQL while budget balance, reservation and cost chain remain unchanged. There is no capacity/consumption permit, correction/overwrite/deletion, external export or payment operation. Corrections and accounting adapters remain separate work.

Lost commit acknowledgement is UNKNOWN and requires later explicit identical replay with current authority; absence alone is not proof of rollback. Begun SQL is awaited and no cancellation/deadline service is introduced. Host database/pool/transaction/concurrency and current-authentication limits remain required. Embedded tests are not independent TCP-session qualification; production receipt/identity/session/key/TLS/failover/throughput/live services remain unqualified.

Initial checkpoint: four actual canonical-migration/restricted-login PGlite groups pass for exact binding/balance preservation, bounded invalid allocations/stale revision, contenders/historical replay and unsettled/released/zero charges. Historical-edition verification was tightened during source review; full tests, installed exports, expanded adversarial tests and current-head CI remain required.
