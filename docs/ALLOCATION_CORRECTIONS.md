# Private allocation corrections (partial RCO-003/005)

`BudgetStore.correctAllocation(context,{budgetId,reservationId,expectedCorrectionRevision,lines,reason},commandId)` appends an explicit private bookkeeping correction. `loadAllocationCorrection(context,budgetId,reservationId,revision?)` reads the latest or an exact historical edition. The original `loadAllocation` continues returning the immutable original allocation. No caller should present an historical correction acknowledgement as the current allocation.

Each correction binds the original allocation revision1 and its exact predecessor correction edition (null only for the first). One deterministic correction record holds up to64 immutable editions using the Resources OWN operational DB and unchanged pinned Evidence SQL SDK. Expected revision0 starts the lineage, later commands require the current correction revision. No branch, reset, removal or silent overwrite is exposed. At the cap the adapter fails closed without eviction; further corrections require a separately reviewed extension. Every read/replay verifies all preceding editions and the current/original budget charge binding. Corruption or missing history fails closed.

Lines have the same bounded, exact project/contributor/unit profile and balance as the original allocation; a nonempty reason of at most1000 characters is mandatory. Lines must change from the preceding allocation. These remain opaque private accounting labels, not contributor identity, entitlement, legal authority or an external receipt attestation. A correction cannot change charge amount, unit, receipt, reservation, budget balance/capacity or execution authority. There is no payment, export, tax, invoice, licensing, deletion or provider action.

Current listed host-authenticated human owner AND current stored budget operator/purpose/source checks occur under the owning project lock before cached acknowledgement lookup. Expected revisions and atomic correction/audit/outbox writes serialize changes. Historical identical replay returns its original edition without creating another change, even if later corrections exist. An unknown acknowledgement requires explicit identical replay with current authority; no response or absent record is not rollback proof. Begun SQL is awaited; host driver/transaction/concurrency limits and current identity/roles/session/configuration/time remain trusted. No cross-service atomic permission fence or new authentication route is claimed.

Initial three actual canonical-migration/restricted-login PGlite groups and strict typecheck pass: exact source/predecessor/history/budget preservation, competing editions/idempotency and invalid bounded input. Broader adversarial tests, installed compiled exports, independent network-session coverage, source review and final-head CI remain pending. Production identity, accounting, receipts, TLS/failover/throughput and deployed acceptance remain unqualified. All fixtures are fictional and no provider/payment network is used.
